# Security

> Each mitigation below is marked **[implemented]** or **[planned]**. The MSI, the service as
> SYSTEM and the checks marked "Sandbox test" are tested in Windows Sandbox.

Endpoint Toolbelt lets a standard user trigger work that runs as LocalSystem. This
document lists the threats that come with that and how the design addresses them,
including what it does **not** protect against.

## Trust boundaries

1. **App (user) -> service (SYSTEM)** over the named pipe `\\.\pipe\EndpointToolbelt`.
2. **Service -> engine** (child `EndpointToolbelt.Engine.exe`, SYSTEM).
3. **Engine -> files, registry and event logs** that other principals may write.
4. **Installer (SYSTEM) -> file system and registry.**
5. **Trusted service caller (an administrator-named service) -> service** over
   `\\.\pipe\EndpointToolbelt.Caller`, only while the policy value `TrustedServiceCaller` is set.

## Principles

- The service is the only privileged component and the only executor.
- User input that reaches SYSTEM is limited to a request type, an action enum,
  confirmation flags, (for client-reported events) a short, cleaned text and (for Get a new
  IP address only) a network adapter's interface index, a positive number the engine only looks
  up among the physical adapters it reads itself. Nothing from the user becomes a path, an
  argument or a script. **[implemented]**
- The service writes, deletes and archives only in its own SYSTEM-only working folder,
  with one exception: its logs in the IME Logs folder, which belongs to another
  product. The engine changes only the system locations its actions name (IME state and
  folders, `SoftwareDistribution`, devices and servicing packages), which standard users
  cannot write, plus the one user-profile exception below. **[implemented]**
- The app name cache (`AppNames.json`: app ID, name, first and last seen; no user, device,
  intent or path) lives directly in the SYSTEM-only working folder; it is the one file there the
  engine writes too. The service and its engine write it only when that folder passes the working
  folder's SYSTEM-only policy and has no reparse point in its path, atomically (a temporary file
  next to it, written through, then one replace), and read it by handle without following a link (a
  link or a hard-linked file is refused, at most 32 MB). A file that cannot be read is ignored and
  rebuilt, never fatal. The engine takes its path only from the service's request, only as an
  absolute local path named `AppNames.json`. At most 2,000 entries, none older than 180 days. Once an
  hour the service reads the IME logs' policy lines for it in the background (the same read-only,
  by-handle, size-bounded read as the engine's; links left out). Its
  names are used only for app rows the user may already see; the support package names it by its
  size and newest date only. **[implemented]**
- A missing protected folder is created *born-locked* (final security descriptor in
  the create call, under a random name, verified, then renamed into place). An
  existing working folder is accepted only if it is a real directory owned by SYSTEM
  or Administrators with exactly the expected DACL; otherwise it is moved aside.
  Subfolders must simply inherit; otherwise they are replaced. **[implemented]**
- The installer never touches user profiles; per-user data stays on uninstall (verified in
  Windows Sandbox). **[implemented]**
- The engine touches user profiles for one purpose only: a Full IME reset deletes
  Company Portal's local app status cache (`AppData\Local\Packages\Microsoft.CompanyPortal_8wekyb3d8bbwe\LocalState\Win32LocalAppStatus.json`)
  in each user profile, so Company Portal asks Intune for the app status again. Profiles
  come from the ProfileList key (local, domain and Entra user SIDs only, local absolute
  paths). The delete runs only while Company Portal is closed and the IME is stopped. The
  engine never ends Company Portal (or any process): the app asks the user to close it first, and
  a full reset that finds it running stops before it changes anything. Only
  the profile root is opened by path (it may be an FSLogix mount point). Each folder below
  it is opened relative to its already-opened parent handle (`NtOpenFile` with
  `OBJ_DONT_REPARSE` and `FILE_OPEN_REPARSE_POINT`, never by full path, which a swap could
  race), held without delete sharing, and refused if it is a reparse point; on a Windows
  build without `OBJ_DONT_REPARSE` the open fails and nothing is touched. The file itself is
  opened the same way, refused when it is a link, has more than one hard link or sits on
  another volume than the profile root, checked to resolve (final path) back to exactly the
  expected path, and deleted through that handle. Where available the process enables
  RedirectionGuard (RedirectionTrust enforcement) first, reads the policy back and logs whether it is on. Nothing else in the profile is read
  or changed, so nobody is signed out. A profile where FSLogix has made
  `AppData\Local\Packages` (or any folder on that path) a junction is refused with a warning
  on every run, by design: the one cache file is not cleared there, and the reset reports
  `FULLRESET-PARTIAL`. **[implemented]** The compiled engine runs the same delete code,
  from the platform library.
- The product never changes the security descriptor of a parent folder it does not
  own. **[implemented]**

## Threats and mitigations

| Threat | Mitigation |
|---|---|
| A user creates the pipe first (squatting) and feeds fake results or a fake package to another user's app | **[implemented]** The service creates the pipe with `FILE_FLAG_FIRST_PIPE_INSTANCE` and fails loudly (event 1014) if the name is taken; while it runs, a listening instance always exists. The app trusts the server only if the pipe is owned by SYSTEM or Administrators, the service is in the Running state, and the server process is that service's process in session 0. Squatting stays possible whenever the service is not running (delayed start, a stop or a crash, or an MSI repair a standard user starts); the app's checks are what hold in all cases, so squatting can at most deny service. **[implemented]** The shipped service has no console mode: before, `EndpointToolbelt.Service.exe --console` let a standard user run the product's own (signed, allowed) binary on the real pipe names, including the trusted caller pipe, during such a window; it is now in Debug builds only (internal security review 2026-10). |
| Remote clients | **[implemented]** `PIPE_REJECT_REMOTE_CLIENTS` on every instance; NETWORK denied in the pipe DACL. |
| A user creates extra pipe instances | **[implemented]** INTERACTIVE gets `0x120083` (read/write data, read attributes, read control, synchronize), never `FILE_APPEND_DATA` (= create pipe instance). |
| Caller impersonation | **[implemented]** The caller's SID and session ID come from the caller's own token (impersonation at Identification level after the request is read); anonymous callers are refused. |
| User input injected into a command line, path or script | **[implemented]** Requests carry only enums and flags; the engine is started with fixed arguments, correctly quoted. There is no configurable repair source or other free-text setting that reaches a command line. Client-reported event text is limited to printable characters without `%`. Get a new IP address adds one number, the adapter's interface index (positive, for that action only, refused otherwise); the engine looks it up among the physical adapters it reads itself and passes it only into its own WMI query, never into a command line. |
| App Control or AppLocker policy bypass | **[implemented]** The product installs no script file and hosts no PowerShell, so there is no execution policy to bypass. When App Control for Business, AppLocker, a Defender attack surface reduction rule or other security software refuses the engine executable, the service reports `EngineNotSigned` (event 1013) from the start error (577, 1260 or 5). The three in-box cmdlets run with a constant `-Command` that works in ConstrainedLanguage mode, never `-ExecutionPolicy`; a policy refusal is named in a finding, never worked around (see [deployment.md](deployment.md#signing)). |
| A user replaces engine files that SYSTEM runs | **[implemented]** Before every run, the service checks that `EndpointToolbelt.Engine.exe` exists and that the install folder, every file directly in it (the libraries the engine loads), the `Engine` folder (the IME log pattern table) and every file below it have owner SYSTEM, Administrators or TrustedInstaller, no write rights for anyone else (generic rights included), no links and no hard-linked files. Otherwise the engine is not started (event 1020). A file that cannot be opened (another process holds it without sharing) is checked once more after 3 seconds; when it still cannot be opened, the user is asked to try again in a minute, because only a link, a hard link or a folder that is not protected needs a repair or reinstall. The check does not cover ancestors above the install folder; installing under `C:\Program Files` is assumed. |
| A user replaces the service's own files | **[implemented]** The MSI's directory IDs are private, so the install folder cannot be moved on the command line (below `C:\` every user could change the files). At start the service checks its own folder and every file directly in it the same way, and the install folder's parents below the volume root (the publisher folder and Program Files: whoever can change a parent can rename the install folder away and put another one in its place; the MSI keeps the ACL of a publisher folder that already existed, so a weak one is refused, not changed, also checked before every run), and refuses to start otherwise (event 1020, and the reason in its log). This catches a changed ACL; it cannot undo a replacement that already happened, because the replaced file is what runs. The Sandbox test weakens the service file's ACL and checks the refusal. Found in the internal security review. |
| A user skips the app's confirmations by calling the pipe directly | **[implemented]** A confirmation counts only with a nonce the service issued to that caller in a status answer within the last 15 minutes, once: a client that never asked for the status (and so never showed the warning) gets `ConfirmationRequired`. A user who writes their own client can still ask for the status and echo the nonce, so this protects against accidental clicks and against a client that confirms blindly, not against a determined local user. What a direct caller cannot skip: the single worker, the per-user rate limit, `AllowMachineWideOnMultiSession=0`, the refusal when the other sessions cannot be counted, and the engine's cooldowns. `AllowMachineWideOnMultiSession=0` blocks full reset and update repair only while other users are signed in; a user who is alone on a multi-session host can still run them. Organizations that never want users to run them on shared hosts do not deploy the product there, or deploy it to those hosts with both cooldowns set high. |
| One user floods or blocks the service | **[implemented]** Requests at most 64 KB, read within 5 s; at most 4 open connections per user (including Watch connections) and 128 in total; a connection whose account cannot be determined from the client process is refused rather than counted in a shared bucket; sends to a client that stops reading time out (30 s) and drop that client; single worker with an explicit `Busy` reply; per-user limits for actions that change the device (default 20 per hour; creating a support package does not count, but on a shared device it has its own limit of 4 per user per hour; the read-only app diagnosis and the read-only Windows Update check do not count either and share a limit of 30 per user per hour on every device), status (60 per minute), last result (20 per minute) and client events (30 per hour). |
| A user wipes the audit trail by flooding rejected requests | **[implemented]** Rejections are logged and evented at most 10 times per user per 10 minutes. **[implemented]** The same holds for refusals at the pipe itself (too many connections, an unreadable request, a client without a usable identity), keyed by the client process's account, with one line saying that further ones are not logged; before, a loop of refused connections could push the "requested by" lines out of the rolling service log within minutes (internal security review 2026-10). |
| One user's action affects other users' sessions on a multi-session host | **[implemented]** Full reset, update repair, Free up disk space and Get a new IP address need the other-sessions acknowledgement; when the sessions cannot be counted, they are refused; organizations can block them while other users are signed in with `AllowMachineWideOnMultiSession=0` (not when the user is alone on the host). **[implemented]** The light refresh (IME restart, Company Portal close, retry-timer clear) is skipped while other users are signed in or when they could not be counted. **[implemented]** The Windows Update repair never stops the update services to clear the cache while other users are signed in (or cannot be counted) or on a multi-session edition. |
| One user reads or replaces another user's results or package | **[implemented]** Results and packages are stored per SID in the SYSTEM-only working folder and delivered over the pipe only to that SID. Other users see only that an action is running, never which user or its content. |
| One user sees another user's line-of-business apps | **[implemented]** The app diagnosis reads MSI line-of-business apps from the MDM stack's record only for the device (a SID that starts with S-0-0-00-) and the caller's own SID; other SIDs are counted, never read or named. The records carry "device" or "user", never a SID, and the download address only as its host. Store apps are the IME's and follow the same scopes. The support package (`MsiApps.csv`, the tab "MSI apps") uses the same readout and the same rules. MSIX line-of-business app installs are read through the MDM WMI Bridge for the device's partition and the caller's own (a user SID only); other users' partitions are never asked. Only the package family name, Status and LastError are read (not LastErrorDesc, free text that can name paths), and the installed version from the inventory; the records carry "device" or "user", never a SID. The support package (`MsixApps.csv`, the tab "MSIX apps") uses the same readout. |
| Forged or echoed engine output | **[implemented]** Only standard-output lines that are JSON objects carrying the current run ID count as records; lines longer than 64 KB are dropped; only the first `file` record counts, and its name must be a plain `.zip` name (no device names). Stored records are capped at 256 KB per run; info progress, then other progress and warning records make room first, and the summary and restart-required records keep 8 KB of their own (and, as a last resort, may push out the oldest findings and changes), so a flood of records cannot push the result out. |
| A stop, restart or power loss hides what a run did | **[implemented]** A run is stored as in progress when it is accepted and saved again (at most every 5 seconds, written through) after findings, changes and closing records. A stop cancels the engine first, refuses new connections, tells connected apps in parallel (3 s in total; not after a pipe fault or at system shutdown), waits up to 15 s from the cancel for the result to be stored, then closes the connections: about 23 s in total, under the 25 s an upgrade allows. Such a run, and a stored run still in progress at the next service start, ends as `Interrupted` (event 1002) with the records saved up to then. |
| A user plants a link or hard link that SYSTEM follows | **[implemented]** The service opens its log files and produced packages with `FILE_FLAG_OPEN_REPARSE_POINT` and refuses them when they are links or have more than one hard link; deletes never follow junctions or links. The engine opens its log by handle like the service and refuses links and hard links; its deletes in the IME folders rely on those folders being writable by SYSTEM and Administrators only. The IME Logs folder is used only while it is owned by SYSTEM, Administrators or TrustedInstaller, has no write rights for others and no reparse point in its path; it is re-checked at least every minute, with a fallback to the working folder and event 1015. **[implemented]** The log folder is pinned by handle (a real directory, not a reparse point, at its expected final path; owner and DACL read through the handle) and the log file is opened, rolled over and protected relative to that handle with `OBJ_DONT_REPARSE`, so nothing between the folder and the file can be swapped after the check. The engine's deletes in IMECache, `Content\Staging` and `Policies` open the root by path (refused when it is a reparse point), every entry below it relative to its pinned parent, on the root's volume only, and delete through the entry's own handle. **Limit:** the ancestors' DACLs are still not checked; the folders rely on the default protection of `%ProgramData%\Microsoft` and `%ProgramFiles(x86)%`. **[implemented]** Every file the engine copies into the support package, and every IME log it parses for app names, is opened by handle without following reparse points, and refused when it is a link, a folder or a file with more than one hard link; the checks and the read use the same handle. |
| A user tampers with tool output that SYSTEM parses (e.g. DISM or SFC output) | **[implemented]** Output of DISM, SFC, pnputil and the Windows Update worker is captured through pipes in memory, never through files; every tool is started by its full System32 path. |
| Forged events steer decisions | **[implemented]** The product's own events are written by the service; the app's events are marked client-reported. The service never registers an event source: it writes through `RegisterEventSource`/`ReportEvent` (which never create one) and only while the MSI's source exists under the product's own log, so a missing registration cannot end up as a source or as entries in the Application log. **[implemented]** The product's event log accepts writes only from SYSTEM and Administrators (`CustomSD`; a standard user's write is refused in the Sandbox test). **[implemented]** MDM event reads filter on log, provider name and event ID, with no unfiltered fallback; a sync counts only with a matching session start and end. The MDM /Sync and /Admin channels accept writes from interactive users, so an event counts only when the process that wrote it (recorded by the event log) is not running in a user session (Windows also runs MDM sessions for user-scoped policies in the user's session, seen on every sync on a real test device: their events are left out as evidence too, which the device session's events make up for, and the engine logs this as information, not as a warning); a writer that has already exited cannot be checked and is accepted (the service's "Last MDM sync" status, shown to every user, applies the same writer check), which leaves a user able to fake their own sync result with a short-lived process (it changes nothing on the device). A retry Windows scheduled (event 286) is honoured for at most 4 hours, so a forged event cannot stop every user's sync for days. **[implemented]** The Windows Update failure events are read with a provider filter as well. The Setup log can be written by any signed-in user, so a failure code seen only there routes nothing unless the Windows Update client channel (writable by the system only) or the update history confirms it; unconfirmed codes are logged only. Every repair is bounded and limited to quality and security updates. |
| Module or DLL hijack of the engine or service | **[implemented]** The engine is started by full path with an environment rebuilt from a fixed list (PATH with System32 and Wbem only); the child inherits only its three standard handles; the service calls `SetDefaultDllDirectories(System32)` at start. **[implemented]** The engine calls `SetDefaultDllDirectories(System32)` at start, and its in-box cmdlet runner starts `powershell.exe` by full System32 path with `PSModulePath` set to the in-box modules folder only, for three constant allow-listed commands; it inserts only values it checked itself (a drive letter, a protector GUID) and never uses `-File`, `-EncodedCommand` or `-ExecutionPolicy`. For the Windows Update API it starts only itself, by its full path in the checked install folder, in worker mode (`--wu-worker` with one of three operations and, for an install, an update ID it checked to be a GUID). |
| Engine child processes outlive a timeout | **[implemented]** The engine starts suspended inside a Job Object with kill-on-close; on a timeout the whole tree ends and the result says "servicing may still be running". **[implemented]** The engine plans every long step within the service's limit (passed in the request) and stops a step on its own limit; Windows Update API calls run in a separate worker process per search or install, so a hung call can be stopped; nothing further is started behind a stopped servicing step, and a repair waits (bounded) while the servicing stack is busy. A Windows Update repair the service had to stop writes no cooldown stamp (it is written at the close-out); a Full IME reset stamps as soon as the state was wiped. |
| A standard user reads or changes the configuration or the cooldown state | **[implemented]** `HKLM\SOFTWARE\EndpointToolbelt` and its `Config` and `State` keys allow only SYSTEM and Administrators (protected DACL, inherited by subkeys). The service enforces this at every start (and creates missing keys that way), because Windows Installer applies a key's `PermissionEx` only when that key row creates the key, and it creates the root and `Config` while writing their first value; the MSI's own setting covers `State`. Between the MSI writing the values and the service's first start (seconds, during the install) users can read the configuration; nothing in it is secret. Sandbox test: a standard user cannot read `Config`. |
| A standard user restarts the service to reset a limit | A standard user can start an MSI repair, and the repair restarts the service. **[implemented]** The per-user rate limit, the support-package limit and the read-only limit of the app diagnosis and the Windows Update check are kept in `Limits\` in the SYSTEM-only working folder and read back at start; a damaged file starts empty, and hits stamped in the future (a clock set back) are dropped. The cooldowns live in the registry and are stamped before the changing part of an action, so stopping a run (Cancel, a restart of the service) does not leave a repair without a cooldown; when the action changed nothing, the engine puts the old value back. Found in the internal security review. |
| A standard user starts an MSI repair with new property values | **[implemented]** Configuration properties are not marked Secure, so Windows Installer does not pass them to the elevated part of a repair a standard user starts; the Sandbox test checks that the stored value stays. **Depends on the device:** the Windows Installer policies "Allow user control over installs" (`EnableUserControl`) and "Always install with elevated privileges" (`AlwaysInstallElevated`) make Windows Installer pass every public property from a user's command line, so a standard user could then set, for example, `FULLRESETCOOLDOWNHOURS=0`. Both policies are off by default and unsafe for other reasons; keep them off, or set the configuration under `HKLM\SOFTWARE\Policies\EndpointToolbelt`, which the MSI never writes. |
| A standard user's repair stops the service | **Accepted.** An MSI repair started by a standard user stops and restarts the service (Windows Installer runs that part as SYSTEM). A run of another user that is in progress at that moment ends; its result is shown as interrupted after the restart, and the cooldown it stamped stays. The limits and cooldowns survive the restart (see above). Stopping the service only on upgrade and uninstall would leave the service's files in use during a repair and need a restart of the device. |
| Uninstall deletes through a user-controlled path | **[implemented]** `--remove-state` runs only as SYSTEM, deletes the working folder only when its path is absolute, normalized and below `%SystemRoot%\System32\config\systemprofile` (otherwise it reports and does nothing), refuses a working folder whose parent path contains a reparse point, deletes without following links, and removes leftover `.new-*` siblings and `.rejected-*` siblings owned by SYSTEM or Administrators only (a folder with another owner is left alone). In the registry it deletes only the product's `State` key and the root key once nothing but an empty `Config` key is left (64-bit view). **[implemented]** Uninstall touches no user profile. **Not rolled back:** `--remove-state` cannot be undone; when the uninstall fails after it and Windows Installer rolls back, the product comes back without its last results, rate-limit counts and cooldown stamps. |
| Other users read the product's logs | **[implemented]** The engine and service logs name the users who ran an action (SID) and the apps and results of their runs, and the IME Logs folder is readable by every interactive user. Both writers give their log file a protected ACL (SYSTEM and Administrators full control, nobody else), and the rolled-over `.lo_` file from an earlier version too. The service sets it through a handle opened without following links (a hard link is refused); the engine refuses a file that is a link and relies on the folder check (only SYSTEM and Administrators can create files in that folder). Intune *Collect diagnostics* runs as SYSTEM and still collects them. A standard user sees their own runs in the app and in their support package. Found in the internal security review. |
| A user makes SYSTEM run a program of their choice through a new action | **[implemented]** The SYSTEM actions run only fixed programs: tools by full System32 path and `MpCmdRun.exe` from the newest folder under Defender's `Platform` folder, each refused unless the file is in a folder only SYSTEM, Administrators or TrustedInstaller can change and carries a valid Microsoft signature (on the compiled engine, an embedded one: a catalog-only signature is refused). Nothing the user sends becomes a path, an argument or a script: requests stay an action enum and flags. |
| A new SYSTEM action deletes in a location a user controls | **[implemented]** Free up disk space clears the Delivery Optimization cache only through its own cmdlet and the component store only through DISM; it never deletes files itself, and never in `C:\Windows\Temp` or another folder a standard user can create or modify. The user's own `%TEMP%` is cleaned by the app, as the user. |
| The recovery key leaks through the backup action | **[implemented]** Back up recovery key asks BitLocker to back up existing protectors by their ID; the recovery password itself is never read, logged, shown or put in a package. The action never adds, removes or suspends a protector. |
| A user changes the time source or Defender settings through an action | **[implemented]** The time source is used only when it is a plain host name, and it is read from the time service itself, never from the request. Sync clock only starts the Windows Time service and asks for a resync; it never changes the time source or any time configuration. Update Defender definitions only asks Defender to update; it never changes a Defender setting, exclusion or the running mode. |
| New readouts show other users' data | **[implemented]** Compliance checks, configuration profile errors, clock, Defender and the Intune connection readout are device-wide and carry only enumerated values, times, counts, short code-like tokens and the names of disabled Intune enrollment tasks (the name only, as plain text without a GUID); the service reads the MDM admin log by provider name and level (Microsoft documents no meaning per event ID), keeps only CSP paths, result codes and whether the command was a removal from it, never message text, and counts only events written from session 0. The Autopilot and Enrollment Status Page sheet holds tracking states, never secrets. A setting token leaves out every GUID segment of its CSP path (such as the tenant ID in a Windows Hello path), so neither the row, the report nor Copy details for IT shows it; the machine kind is two yes/no values. The app diagnosis keeps from the IME's agent log only the facts of a detection-script run (time, revision, bitness, exit code, whether there was output), never the script, its output or a path. |
| A user-context tool touches another user's profile | **[implemented]** The folders are built from the user's own known folders and must lie inside the user's profile; links are never followed or removed; files in use are left alone. The sign-in cache, Teams cache and `%TEMP%` cleanup run in the app, as the signed-in user, in that user's own profile only; they cannot reach another profile, because the user has no access to it. "Copy details for IT" holds no device or user name, no address and no log lines. |
| The connection check sends something of the user's, or follows the network somewhere else | **[implemented]** Check Microsoft connections runs in the app, as the user, and makes per target one unauthenticated HTTPS request to a fixed Microsoft host (a HEAD to "/", or for sign-in a GET of the public OpenID document, at most 64 KB read): no cookies, no credentials for the service, no redirect followed. The user's proxy may get the user's Windows sign-in, as the user's apps give it, and only that proxy: the sign-in is handed out for the proxy's own host and port only, because .NET Framework follows a proxy's redirect to CONNECT by itself (straight to the redirect's host, a bare `CONNECT <host>:443` without a body), and with the plain default credentials it answered an NTLM or Negotiate request from that host with the user's sign-in (measured on .NET Framework 4.8 with loopback listeners; unit tests keep it closed). The machine proxy never gets credentials, and a 407 is reported, never answered with typed credentials. After a failure or a status through a proxy before any TLS, the check sends that proxy one bare CONNECT for the host (no credentials, nothing sent through a tunnel it opens) to read the proxy's own status. The system's certificate validation decides; a certificate for another name or an untrusted chain ends the request. The run log, the cards and Copy details for IT carry host names, status codes and outcomes only, never a URL, header, cookie or body; a captive portal is named by its host; an inspecting proxy's certificate authority (its organization) appears in the run log and Copy details for IT only. |
| The version check is used to track a device, gives the user's sign-in away, or sends users somewhere else | **[implemented]** Only the app reads the feed, as the signed-in user; the service never reaches the internet for it. The request is one GET of a fixed https address on soulbit.app, made as the connection check makes its requests: no redirect followed (anything but 200 is no offer), no cookie and no credentials for the server, the user's Windows sign-in only for the proxy's own host and port on a proxy object of the request's own, the product name as user agent, no data about the device or the user (the site sees the public address and the time, as every web server). The answer is read strictly (16 KB at most; a version of three ASCII numbers, a date, and release notes over https on soulbit.app or below the product's own repository) and is only shown, never acted on: the app downloads and starts nothing, and a link opens only on a click. The notice's one link, "Release notes", is fixed in the code (the product's page on soulbit.app), not taken from the feed. A failure ends in "no offer". Off means no request by itself: `UpdateCheck` = 0 in policy locks it off, hides About's Check now and makes no request at all, and an unreadable policy key counts as off; the user's choice in About and the installer's `UPDATECHECK=0` (the check box on the first screen of an install a person starts, or the command line) switch the look off too, while Check now in About stays the user's own click for one request. The setup never starts the app: the installer's choice is written by the install itself, before anything runs. Loopback tests cover the redirect, a non-200, the size limit and a server asking for a sign-in. |
| Privacy in the support package | **[implemented]** The package is built in the run's SYSTEM-only folder and delivered only to the user who asked for it. App state and remediation results (in the package and in every action's result) cover only the device and the requesting user's own scope, matched by the Entra object ID in their SID; other users appear only as counts. User scope IDs are shortened to 8 characters. Device-only `dsregcmd` sections from SYSTEM (an allow-list). In the service log in the package the requester's own SID is shortened as the CSV files name that user (User: and 8 characters of the Entra object ID) and other users' SIDs are removed, and so are the lines of their runs (which action, when, from which session; counted in a closing line), and the engine log in the package keeps only the requester's own runs (matched through the "requested by" lines of the service log) plus this run; other users' lines are left out and counted in a closing line. Remediation scripts and the script output stored with their results are never read. The "IME log summary" tab holds phases, exit codes, byte counts, times and error counts only, never log text, install command lines or scripts; the check-in in the health status carries only times and a short code-like error token (letters, digits and '-', at most 40 characters), read by the service by handle without following links. The MDM diagnostics export is the one the signed-in user can also make from Settings, and the IME logs of the Intune Management Extension are readable by interactive users, so neither gives the requester data they could not read already (to be confirmed for a standard user). **[implemented]** The app adds the user's own `dsregcmd` view, device report and history in the user's context, copies the package to the user's Downloads (resolved through the Known Folder API) and checks it against the length and SHA-256 the service announced before it is used. The app name cache (which can hold the names of other users' available apps) is named in the package by its size and newest date only, never as a list. The package takes less, never more: per IME log the current file and its newest older copy (for AppWorkload, IntuneManagementExtension and AgentExecutor every older copy of the last 24 hours; PSADT logs of the last 30 days only; each at most 8 MB, its newest part), no Sensor or Win32AppInventory log, the IME logs taken out of the MDM diagnostics so each is in the package once, and a zip of at most 25 MB (older copies of logs that are not app install logs, then the largest logs that are not core, then older copies of the app install logs, are left out first). Its index (PackageIndex.txt) lists what was taken, cut and left out with sizes only, no device or user name, address or path. **[implemented]** |
| The Defender check shows a standard user more than they may see | **[implemented]** Check Defender blocks reads the Microsoft Defender operational log, which Windows lets only administrators and SYSTEM read, so what it returns is limited on purpose. It reads the events of threat detections, attack surface reduction rules, controlled folder access and network protection (blocks and audits) of the last 14 days, at most 2000, and returns them grouped, at most ten groups. An event is shown only when its user is Windows or a service account (the device) or the caller's own account, matched by SID or by the name Windows gives the caller's SID; an event of any other account, also one Windows cannot resolve, and an event that names no user are counted and nothing of them is returned. A path below the caller's profile is written with `%USERPROFILE%`; a path below any other profile of the profile list, or a folder of the profiles' folder that is no shared profile, is replaced by a fixed text, also in its long form (`\\?\`), as a device or volume path, as a short (8.3) name or below the old "Documents and Settings" name; a device or volume path outside the profiles is written as its file name; a detection's resource that is no file (a command line, a registry value) is named by a fixed word and never shown; a network protection destination is reduced to its host name (no path, query or port, which can carry a token or a person's data), and is shown only for the device's and the caller's own events; only the event values the check uses are read from the event XML (fourteen names: the ten of the blocks, and for the health facts `Changed Type` and `Value` of tamper protection's 5013, which is matched against a fixed list of real-time protection settings and never shown, and `Feature Name` and `Error Code`, shown only as a few plain words and a hexadecimal code), so the command lines the events carry, the update source of a failed update (which can be a share path) and the configuration change event 5007 (whose values can be exclusion paths) are never read; no account name is returned; every value loses its control and format characters (a direction override, a zero-width character) and is cut at 260 characters. The event XML is read without DTDs and without a resolver. The `defender-check` record, the run log line, the history and Copy details for IT hold counts only. What the caller learns about the device (which rule blocked which process) is what Windows Security's protection history and the block notification show a signed-in user; an organization that does not want it switches the tool off with `DisabledTools` (`CheckDefenderBlocks`). The check changes no rule, exclusion or quarantine. |

### Trusted service caller

| Threat | Mitigation |
|---|---|
| The extension point is on where nobody wants it | **[implemented]** Off unless the policy value names a service; a value under the configuration key (which the MSI writes) is ignored; without the policy value no pipe is created and the service behaves exactly as before (tested). |
| Another local process (a user, another service, an administrator's tool) uses the caller pipe | **[implemented]** DACL: SYSTEM (which creates the instances) and the named service's SID only; NETWORK denied; `PIPE_REJECT_REMOTE_CLIENTS`. After the request is read, the client process must be the named service's running process in session 0, with its program file in a folder only SYSTEM, Administrators or TrustedInstaller can change; otherwise the connection is closed and event 1017 written. **Limit:** any process running as SYSTEM can already do everything this pipe offers, and an administrator can change the policy; the extension point does not defend against either. |
| Someone squats the caller pipe name | **[implemented]** The pipe is created with `FILE_FLAG_FIRST_PIPE_INSTANCE`; when the name is taken it stays closed (event 1014). The caller should verify, as the app does, that the pipe server is the Endpoint Toolbelt service's process in session 0. |
| The trusted caller gets more than a user | **[implemented]** Only `GetStatus`, `RunAction` and `GetLastResult`, with the same enums, confirmation flags, other-sessions acknowledgement, `AllowMachineWideOnMultiSession`, rate limits and engine cooldowns as a user (tested). No client events and no Watch. **One exception:** a tool the organization switched off with `DisabledTools` is refused to a user but not to the caller, so the service desk keeps it; this is the organization's choice, made by the same administrators who name the caller (tested). |
| A user runs a tool the organization switched off | **[implemented]** The policy value `DisabledTools` is read from the policy key only (the MSI cannot set it). The service refuses a switched-off service tool from the user pipe with `ToolSwitchedOff` (24) and event 1018 before anything runs, so a user with a client of their own cannot get past it (tested). The app hides every switched-off tool and keeps its button off. **Limit:** the tools that run in the app run as the user without the service (Teams cache, sign-in cache, Company Portal data, safe mode, OneDrive reset, the connection and compliance checks, Bring my window back, Open IME logs); the policy hides them, but a user can do the same by hand, as Windows already allows. An organization that must stop those uses Windows' own controls. |
| Results cross between the trusted caller and local users | **[implemented]** The caller's results and limits are kept under its service SID (`S-1-5-80-...`), which is never a user's SID: a local user never sees the caller's results, and the caller never sees a local user's (tested). |
| A remote run returns another user's data | **[implemented]** The engine includes a user's scope only for the user at the console when that user is the only one signed in; otherwise the device scope only (tested). Responsibility for showing the user that a remote run took place lies with the organization's caller service. |
